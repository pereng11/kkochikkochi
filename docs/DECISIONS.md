# 결정 로그

KkochiKkochi 설계 과정에서 내려진 결정과 그 근거를 기록한다.

**이 문서의 역할** — 설계 문서가 *무엇을 만드는가*를 기술한다면, 이 로그는 *왜 그렇게 정했고 무엇을 버렸는가*를 기록한다. 기각된 대안과 번복 이력이 특히 중요하다. 나중에 "왜 이렇게 안 했지?"라는 질문이 나올 때 다시 논쟁하지 않기 위한 것이다.

**상태 표기**

- ✅ 채택
- 🔄 변경됨 (같은 항목이 세션 중 뒤집힘 — 변경 이력 참조)
- ❌ 기각 (제안되었으나 채택되지 않음)

**작성 규칙** — 결정이 바뀌면 기존 항목을 지우지 않고 상태를 바꾸고 변경 이력을 덧붙인다. 지운 결정은 반드시 다시 논쟁된다.

---

## 제품 정의

### D01. 게이트를 하드 차단으로 만든다 ✅

**결정** 이해를 증명하지 못하면 커밋을 실제로 차단한다.

**맥락** 소프트 게이트(퀴즈를 내되 막지 않고 기록만), 조건부 하드 게이트(위험 변경에서만 차단), 수동 호출 전용이 대안이었다.

**근거** 해결하려는 문제가 "사람의 이해가 병목이자 리스크"인데, 막지 않는 게이트는 바쁠 때 정확히 무시된다. 게이트가 필요한 순간과 무시되는 순간이 같다.

**대가** 급할 때 마찰이 크다. D06(탈출구)과 D16(fail-open)이 이 대가를 완화한다.

---

### D02. 검증 축은 4개 전부 ✅

**결정** 변경 사실 확인 · 영향·리스크 · 설계 의도 · 재현 가능성.

**근거** 축마다 정답의 근거가 다른 곳에 있다. 설계 의도는 diff에 없고 대화에만 있으며, 재현 가능성은 대화에 없고 레포에만 있다. 이 사실이 D07(아키텍처)을 강하게 제약했다.

---

### D03. 오답이면 통과할 때까지 재출제 ✅

**결정** 해설 후 **같은 축 다른 각도**로 재출제. 같은 문항 반복은 금지.

**맥락** 임계 점수제(5문항 중 4개 통과), 1회 재시도 후 기록만 남기고 통과가 대안이었다.

**근거** 학습 효과가 가장 크다. 같은 문항 반복을 금지하는 이유는, 반복하면 코드를 이해해서가 아니라 정답을 외워서 통과하기 때문이다. 게이트의 목적이 정확히 무너지는 지점이다.

---

### D06. 탈출구는 "모르겠다" → 강제 학습 루프 ✅

**결정** 항복 선언 시 에이전트가 해당 지점을 실제 코드 인용해 설명하고, 다른 각도로 재출제한다.

**맥락** `--no-verify` 류 비상 우회, 시도 횟수 상한 후 자동 통과가 대안이었다.

**근거** D01 + D03 조합은 교착 위험이 있다. 그러나 "빠져나갈 수 있는 문"을 만들면 그 문이 기본 경로가 된다. 학습 루프는 무한루프도 아니고 우회도 아니다.

**관련** D14(근거 없는 문항 폐기)가 교착의 다른 원인을 차단한다.

---

### D15. 큰 커밋에 "분할 커밋 권고" 경고를 띄운다 ❌

**결정** 채택하지 않음.

**맥락** 변경 파일 10개 초과 시 경고 문구를 출제 전에 표시하는 안을 제안했다.

**기각 사유** 사용자 판단 — 게이트가 아닌 잔소리를 추가하지 않는다. 도구가 하는 일이 늘어날수록 도구를 끄고 싶어진다.

---

## 아키텍처

### D07. 훅은 문지기, 스킬은 시험관 (A안) ✅

**결정** PreToolUse 훅은 판정만 하고(LLM 없음), 출제·채점은 스킬(LLM)이 담당한다.

**기각한 대안**

| 안 | 내용 | 기각 사유 |
|---|---|---|
| B | 훅이 직접 LLM을 호출해 출제·채점까지 | 훅은 대화 맥락에 접근할 수 없어 D02의 4축 중 "설계 의도"가 원천 불가. 훅 프로토콜은 stdin/stdout 기반이라 TUI 대화형 입력도 불가. 별도 API 키 필요 |
| C | 커스텀 `/commit` 명령 안에 퀴즈 삽입 | 하드 게이트가 아님. `git commit`을 직접 치면 그대로 통과 — D01과 정면 배치 |

**부수 효과** 판정 로직에 LLM이 없으므로 셸 스크립트를 결정적으로 테스트할 수 있다. 게이트가 오작동하면 도구 전체가 버려지므로 이 성질이 가장 중요하다.

---

### D04. 트리거는 커밋 직전 ✅

**결정** `git commit`을 PreToolUse로 가로챈다.

**맥락** 변경 누적 임계치(Stop 훅 + N줄 이상), TODO 전부 완료 시, 매 턴 종료마다가 대안이었다.

**근거** 경계가 명확하고 의미 단위가 크다. 자잘한 수정마다 발동하지 않는다.

**대가** 커밋하지 않는 탐색 작업은 전혀 검증되지 않는다. v1에서 감수한다.

---

### D16. 오류 시 통과시킨다 (fail-open) ✅

**결정** `pending-set.sh` 실패, git 부재, `covered.tsv` 손상 시 경고만 남기고 커밋을 허용한다.

**근거** 하드 게이트에서 fail-closed는 **버그 하나가 레포를 벽돌로 만든다.** 사용자가 커밋을 못 해 플러그인을 삭제하는 것이, 게이트가 한 번 새는 것보다 큰 손해다.

**전제** D10(신뢰 경계)과 같다 — 막으려는 상대는 공격자가 아니라 바쁜 사람의 관성이다. 우발적 누수는 감당 가능한 비용이다.

---

### D10. 신뢰 경계는 규율 장치이지 보안 경계가 아니다 ✅

**결정** 에이전트가 퀴즈를 건너뛰고 `record-pass.sh`를 호출하는 것을 기술적으로 막지 않는다. 방어선은 (1) 빈 문항·공백 서술 거부, (2) 문답 전문의 사후 확인 가능성뿐이다.

**근거** 더 조이려면 훅 안에서 LLM을 돌려야 하는데(B안), 그러면 대화 맥락을 잃어 4축 중 2축이 사라진다. 얻는 것보다 잃는 것이 크다.

---

## 통과 토큰

### D08. 토큰을 파일 단위 blob SHA에 바인딩한다 ✅

**결정** `covered.tsv`의 키는 `(경로, blob SHA)` 쌍. 검증 규칙은 "커밋될 모든 쌍이 합집합 안에 있는가".

**기각한 대안** diff 전체를 통째로 해싱. 단순하지만 **분할 커밋이 매번 재퀴즈된다.** 한 번 이해한 파일을 커밋 횟수만큼 다시 시험보게 된다.

**정확도 손실 없음** 파일을 한 글자라도 고치면 SHA가 바뀌어 그 파일만 무효화되고 나머지는 영향받지 않는다.

**사용자 확인** "분할 커밋 재퀴즈는 안 하는 게 맞음"

---

### D09. HEAD 이동을 무효화 조건에 넣지 않는다 ✅

**결정** `head` 필드는 감사용으로만 기록하고 검증에 쓰지 않는다.

**근거** HEAD를 무효화 조건에 넣으면 D08이 무의미해진다. 분할 커밋의 첫 커밋에서 HEAD가 움직이고, 두 번째 커밋에서 토큰이 죽어 같은 파일을 재퀴즈하게 된다. 무효화는 blob SHA가 이미 정확히 처리하므로 HEAD 검사는 오탐만 추가한다.

---

### D11. 저장 구조를 검증용과 감사용으로 분리한다 🔄

**결정** `covered.tsv`(검증 전용, 자유 텍스트 없음) + `passes/*.json`(문답 전문, 1건 1파일).

**변경 이력** 최초 `passes.jsonl` 단일 파일로 설계 → 같은 날 분리로 변경.

**변경 사유** 단일 파일 안에서는 문답 전문의 자유 텍스트가 검증 경로에 섞인다. 문항이 커밋 해시를 인용하면(`"9f2b1c8e 커밋에서..."`) 훅의 문자열 매치가 엉뚱한 필드에 걸려 **조용한 오통과**가 발생한다. 발견도 되지 않는 종류의 버그다.

분리의 주 목적은 성능이 아니라 이 실패 모드를 구조적으로 불가능하게 만드는 것이다. 부수적으로 훅 스캔이 빨라지고 감사 로그도 사람이 읽을 수 있게 된다.

---

### D18. TTL · 자동 트림 · 취약도 리포트는 v1 범위 밖 ✅

**결정** 만들지 않는다. 단 `at` / `axis` / `attempts` / `gave_up` 필드는 **처음부터 기록한다.**

**근거** 기능은 나중에 추가할 수 있지만 데이터는 소급 생성할 수 없다. 스키마만 미리 확보한다.

---

## 트리거 정책

### D12. `git commit --amend`(내용 변경)를 게이트 대상에 포함한다 🔄

**결정** 게이트 대상.

**변경 이력**
1. 최초 — 게이트 대상 (내용이 추가되므로)
2. 변경 — 게이트에서 제외 (amend는 빈번한 워크플로라 마찰이 큼)
3. 최종 — 다시 게이트 대상 ✅

**최종 근거** 제외하면 명백한 누수 경로가 생긴다. 적대적 시나리오가 아니라 평범한 워크플로에서다 — 작은 파일 하나 커밋(퀴즈 통과) → "아 빠뜨렸네" → amend로 나머지 전부 얹기. 얹힌 것은 한 번도 검증되지 않는다.

**부수 효과** 포함하기로 하니 **특수 코드가 아예 필요 없어졌다.** `git diff --cached`가 HEAD 대비 새 델타만 주므로, 메시지만 수정하면 자동으로 빈 집합이 되어 통과하고 내용을 얹으면 그 델타만 대상이 된다. 설계가 더 단순해졌다.

**폐기된 파생 결정** D12 제외안을 위해 제안했던 `amend-unverified` 로깅(게이트는 안 걸되 미검증 유입을 기록)은 구멍이 사라져 불필요해졌다.

---

### D13. revert · cherry-pick · merge는 통과시킨다 ✅

**결정** 게이트하지 않는다.

**근거** revert는 **비상 레버**다. 장애 상황에서 롤백 앞에 퀴즈를 띄우면 게이트가 사고를 키우는 도구가 된다. 게이트의 목적은 위험한 것을 배포하기 전에 이해시키는 것이지, 위험을 되돌리는 것을 늦추는 게 아니다. **탈출구에 자물쇠를 다는 설계는 항상 잘못됐다.**

**기술적 확인** `git revert`는 `git commit`을 거치지 않고 자체적으로 커밋을 만든다. 매처가 `git commit`만 보면 자연히 통과하므로 별도 처리가 필요 없다.

**부수 성질** revert 후 다시 되돌리면 내용물이 원래 blob SHA로 복귀하므로 토큰이 되살아난다. 같은 코드를 두 번 묻지 않는다.

## 문항

### D05. 하이브리드 형식 — 객관식 + 서술 1문항 ✅

**결정** 사실·영향 확인은 객관식, 설계 의도는 서술.

**맥락** 전원 객관식(마찰 최소, 찍기 가능), 전원 서술형(검증 엄격, 타이핑 부담), 코드 지적형이 대안이었다.

**근거** 객관식만으로는 소거법 통과가 가능하고, 서술형만으로는 시간 목표(D19) 안에 끝나지 않는다.

---

### D17. 문항 예산은 상한 5, 억지로 채우지 않는다 🔄

**결정** 상한 5문항, 하한 1문항. 근거 있는 문항만 출제한다.

**변경 이력**
1. 최초 — 변경 규모별 스케일링 (파일 3개 이하 4문항 / 4~10개 6문항 / 10개 초과 8문항)
2. 변경 — 상한 3 고정 ("1분 목표" + "억지로 채우지 말 것" 반영)
3. 최종 — 상한 5 ✅

**최종 근거** 사용자 판단 — 상한 3은 너무 작다.

**시간 목표와의 관계** 상한 5는 전부 정답이어도 약 100초라 당시 목표였던 1분을 넘겼다. D19에서 시간 목표를 3분으로 늘려 해소했으므로, 상한 5는 오답 루프까지 포함해도 목표 안에 들어온다.

**하한의 예외** 질문할 거리가 전혀 없으면(lockfile 재생성, 포매팅만) 0문항 + 사유 기록 후 통과. `package-lock.json`에 퀴즈를 내면 도구가 웃음거리가 된다.

---

### D19. 시간 목표는 3분 🔄

**결정** 상한 5문항에 오답 루프까지 포함해 3분.

**변경 이력**
1. 최초 — 2~3분
2. 변경 — 1분으로 단축
3. 중간 — D17(상한 5)과 산수가 충돌해, 1분을 "상한"이 아니라 "전형값 목표"로 의미 재정의
4. 최종 — 3분 ✅

**최종 근거** 사용자 판단. 3분으로 늘리면 의미 재정의라는 우회가 불필요해진다. 상한 5문항이 전부 정답일 때 약 100초이므로, 3분은 오답 루프 몇 회까지 흡수하는 **진짜 상한**이 된다.

| | 문항 수 | 소요 |
|---|---|---|
| 전형값 | 2~3 | 약 40~65초 |
| 상한, 전부 정답 | 5 | 약 100초 |
| 상한, 오답 루프 포함 | 5 + 재출제 | 3분 |

**남은 긴장** 매 커밋마다 발동하는 게이트에 3분은 짧지 않다. 지속 가능성이 실사용에서 검증되어야 할 가정으로 남는다. 3분을 넘는 경우는 문항이 과하거나 변경이 지나치게 크다는 신호로 본다.

---

### D20. 오답 선택지 품질 규칙 ✅

**결정** (1) 오답은 "그럴듯한 오해"에서 뽑는다 (2) 레포의 실제 문자열을 사용하고 지어낸 이름은 금지 (3) "변함 없음"·"위 전부"·"해당 없음" 금지 (4) 정답 위치 무작위화.

**근거** LLM이 자기가 쓴 코드에 문제를 내면 오답이 너무 티가 나서 코드를 읽지 않고 소거법으로 통과할 수 있다. **이 실패가 발생하면 게이트 전체가 무력화된다.** 문항 품질이 이 도구의 성패다.

---

### D14. 근거를 특정할 수 없는 문항은 출제 전 폐기한다 ✅

**결정** 모든 문항은 정답 근거를 `파일:줄` 또는 `대화 내 발언`으로 특정할 수 있어야 한다.

**근거** D01(하드 차단) + D03(통과할 때까지) 조합에서 **가장 치명적인 실패는 LLM이 낸 정답이 틀린 것**이다. 사용자가 맞는 답을 하는데 계속 오답 처리되면 D06(탈출구)조차 소용없이 진짜로 갇힌다. 추측성 문항이 게이트에 들어가는 순간 이 도구는 신뢰를 잃는다.

### D23. `hooks/`와 `scripts/`를 호출 주체로 나눈다 ✅

**결정** `hooks/gate.sh`(훅만 호출), `scripts/pending-set.sh`·`scripts/record-pass.sh`(스킬도 호출).

**맥락** 조사한 플러그인들의 관례가 갈렸다. `ralph-loop`는 훅 진입점만 `hooks/`에 두고 사용자 유틸은 `scripts/`에, `security-guidance`는 훅 관련 코드를 전부 `hooks/`에, `superpowers`는 둘 다 쓴다.

### D24. 훅 설정의 `if` 필드를 쓰지 않는다 ✅

**결정** `matcher: "Bash"`로 넓게 받고 `gate.sh` 안에서 커맨드를 직접 파싱한다.

**맥락** 훅 항목에는 `"if": "Bash(git commit:*)"` 같은 세밀한 매처가 있고 `security-guidance`가 실제로 사용한다.

**기각 사유** 이 문법은 접두 매칭이라 `cd sub && git commit`이나 `git -C path commit`을 놓친다. 게이트에서는 누락이 곧 실패다. 파싱 비용은 무시할 수준이고, 놓친 커밋은 되돌릴 수 없다.

**변경 이력 (구현 후)** "파싱 비용은 무시할 수준"이 틀렸다. 이 훅은 **모든** Bash 호출에 붙는데 토크나이저가 커맨드 길이에 O(n²)였다(측정: 20 KB → 4.0 s, 10 s 타임아웃을 35 KB 근처에서 초과). 두 가지로 고쳤다. (1) `case "$cmd" in *commit*)` 사전 필터 — `parse_git_commit` 은 리터럴 `commit` 토큰을 요구하므로 이 필터로 놓치는 커밋은 존재할 수 없다. (2) 토크나이저를 1024바이트 조각 단위로 돌려 사실상 선형으로 만들었다. 타임아웃으로 인한 fail-open 은 "조용히 게이트가 꺼지는" 경로이므로 성능은 여기서 정확성 문제다.

---

### D25. 커맨드 파서는 하나뿐이다 (`scripts/lib-tokenize.sh`) ✅

**결정** `gate.sh` · `pending-set.sh` · `record-pass.sh` 가 같은 파일의 `tokenize_cmd` / `parse_git_commit` 을 source 해서 쓴다. 이 lib 은 아무것도 의존하지 않는다(의존 그래프는 여전히 비순환).

**맥락** 초기 구현에서는 `gate.sh` 가 따옴표를 이해하는 상태 기계로, `pending-set.sh` 가 `${CMD#*git }` + `set -- $ARGS` 로 *같은 문자열*을 각각 파싱했다.

**근거** 파서가 둘이면 답도 둘이다. 실제로 세 개의 critical 이 전부 이 하나의 결함에서 나왔다 — 따옴표 안의 `--` 로 게이트가 통째로 꺼지는 것, bare pathspec 누락, 그리고 스킬이 훅과 다른 커맨드를 가정해 생기는 영구 교착. D07(단일 진실 공급원)은 "같은 스크립트를 부른다"로는 부족하고 "같은 파서를 쓴다"까지 가야 성립한다.

### D26. `pending-set.sh` 는 스테이징 하한 + 옵션 화이트리스트로 never-shrink 를 만든다 🔄

**결정** 출력은 언제나 `git diff --cached --raw` 의 집합을 **포함**한다. 스테이징된 집합을 먼저 낸 뒤, 커맨드가 더 담는다고 말하는 만큼만 더한다. 인식하지 못하는 토큰이 하나라도 있으면(목록에 없는 옵션, `-p`·`--interactive` 같은 대화형) 워크트리 수정본까지 합집합으로 낸다.

**기각한 대안** 계획서 원문의 "오파싱은 과잉 방향뿐이라 안전하다"는 사례별 추론. 이 전제는 **거짓**이었고(누락 방향으로도 샜다), 그 전제 때문에 두 결함이 두 번의 리뷰에서 minor 로 미뤄졌다.

**근거** 비대칭이 극단적이다 — 과잉은 사용자가 문항 몇 개를 더 푸는 비용이고, 누락은 게이트가 아무 신호 없이 꺼지는 실패다. 안전한 방향이 기본값이어야 한다.

**대가** `--only <path>` 처럼 git 이 실제로는 스테이징된 다른 파일을 담지 않는 경우에도 그것을 포함한다. 알면서 감수한다.

**변경 이력 (1차 수정 리뷰 후)** — 원문은 이 항목을 "never-shrink 불변식을 **코드 구조로 강제**한다", "안전한 방향이 **유일하게 도달 가능한** 방향" 이라고 썼다. **그 주장은 과했다.** 자동으로 보장되는 것은 **스테이징 하한** 하나뿐이다(항상 `emit_staged` 를 먼저 낸다). 그 위에 무엇을 더 얹을지는 `case` 문의 **손으로 관리하는 옵션 화이트리스트**가 결정하고, 목록에 있으면 "안다"고 보고 넘어간다. 즉 사람의 판단은 사라진 것이 아니라 사례별 추론에서 목록 관리로 옮겨간 것뿐이다.

실제로 그 목록에 틀린 항목이 둘 있었다. `--pathspec-from-file` 과 `--pathspec-file-nul` 은 커밋될 경로를 **파일 안에서** 읽는데, 이 스크립트는 그 파일을 읽지 않으면서도 두 옵션을 "아는 옵션" 으로 등록해 두어 `unknown` 이 켜지지 않았다. 결과는 C2 와 완전히 같은 부류의 누락 — 파일에 적힌 경로가 통째로 게이트를 빠져나갔고, 게이트는 그 커밋이 담지도 않는 파일로만 deny 했다.

그래서 이 결정은 **불변식이 아니라 화이트리스트**로 기술한다. 다음 사람이 목록에 항목을 추가할 때 그것이 스타일이 아니라 **안전성 판단**임을 알아야 하기 때문이다. 목록에 무언가를 넣기 전에 반드시 답할 것: *"이 옵션이 무엇이 커밋되는지를 바꾸는가?"* 그렇다면 넣지 말고 `unknown` 으로 떨어뜨린다. `tests/command-forms.bats` 의 "화이트리스트 감사" 테스트가 파일 집합을 바꾸는 옵션들을 계속 검사한다.

### D27. 경로를 내는 모든 git 호출에 `core.quotePath=false` ✅

**결정** `pending-set.sh` 의 모든 경로 산출 호출을 `git -c core.quotePath=false` 로 감싼다.

**근거** git 기본값(`true`)에서 비ASCII 경로는 C 이스케이프된다(`"\355\225\234\352\270\200.ts"`). 그러면 `[ -e ]` 가 실패해 `NULL_SHA` 가 나오는데, `NULL_SHA` 는 **내용과 무관**하다 — 한 번 커버되면 그 파일은 어떻게 바뀌어도 다시 묻지 않는다. 한국어로 쓰인 도구에서 한글 파일명은 예외가 아니라 기본 사례다.
