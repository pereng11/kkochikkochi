# KkochiKkochi v2 — 하이브리드 게이트 설계

작성일: 2026-07-30
대체 대상: `2026-07-29-kkochikkochi-design.md` §4, §6, §8, §9 (나머지 절은 유효)

---

## 0. 기준점

> **우리가 푸는 문제는 "AI가 사람이 흡수하는 속도보다 빠르게 코드를 만든다"는 것이다.**
> **따라서 이 도구는 에이전트가 만든 커밋에서만 켜진다.**
> **다만 정확한 타이밍을 보장하고 깔끔하게 동작하기 위해 git 훅 기반으로 설계한다.**

이 문서의 모든 결정은 위 논지(D00)에 비추어 판단한다. 특히 **"막아야 할 커밋을 정확히 막는 것"이 목표이지 "더 많이 막는 것"이 목표가 아니다.**

## 1. 왜 v1을 바꾸는가

v1은 Claude Code의 `PreToolUse` 훅에서 **bash 명령 문자열을 파싱해** 그것이 `git commit`인지, 무엇이 커밋될지를 알아내려 했다. 구현과 세 차례의 수정 웨이브에서 나온 결함이 거의 전부 이 한 곳에서 나왔다.

| 결함 | 증상 |
|---|---|
| C1 | 인용된 메시지 안의 `--` → 게이트 무력화 |
| C2 | 맨 pathspec → 누락 포함 |
| B1 | `--pathspec-from-file` → 해당 파일들 미검증 통과 |
| 개행 | `echo hi⏎git commit -m x` → 통과 |
| N1 | 마커 계산 O(n²) → 타임아웃 → fail-open 통과 |
| — | 토크나이저 O(n²), 청크 경계, `'\''` 이스케이프, `-C` 대상 저장소 |

세 웨이브 모두 목표는 정확히 닫았고, 세 번 모두 같은 부류를 새로 열었다. **결함이 아니라 접근이 문제다.**

## 2. 핵심 발견 — git이 답을 알고 있다

git이 직접 호출하는 `pre-commit` 훅은 **커밋될 내용을 정확히 본다.** 측정 결과:

| 명령 | 훅 실행 | 훅의 `git diff --cached` | v1이 원한 정책 | 일치 |
|---|---|---|---|---|
| `git commit` | ✅ | 정확 | 게이트 | ✓ |
| `git commit -a` | ✅ | 워크트리 반영해 정확 | 게이트 | ✓ |
| `git commit -- <path>` | ✅ | 정확 | 게이트 | ✓ |
| `--pathspec-from-file` | ✅ | 정확 | 게이트 | ✓ |
| `--amend` | ✅ | 델타만 | 게이트 (D12) | ✓ |
| `revert` | ❌ | — | 통과 (D13) | ✓ |
| `cherry-pick` | ❌ | — | 통과 (D13) | ✓ |
| `merge` | ❌ | — | 통과 (D13) | ✓ |
| `--no-verify` | ❌ | — | — | ⚠ |

**v1이 코드로 구현하려던 트리거 정책 전부가 git 자체 동작에서 공짜로 나온다.** D12와 D13은 이제 구현 대상이 아니라 관찰된 사실이다.

## 3. 아키텍처

```
git commit
   │
   ├─ [1] 에이전트 훅 (Claude Code / Codex)  ── 안전 경로 아님
   │        · 이 훅이 발동했다 = 에이전트다 (정의상 참)
   │        · 마커를 남긴다 → §4 핸드셰이크
   │        · git 훅 설치 여부 건강검진 → §6
   │        · --no-verify 감지
   │
   └─ [2] git pre-commit 훅  ────────────────── 진짜 게이트
            · 에이전트가 만든 커밋인가?  → 아니면 통과 (D00)
            · git diff --cached --raw  ← 커밋될 내용 그 자체. 파싱 없음
            · covered.tsv 와 대조 → 미검증이면 exit 1
```

### 3.1 리스크 방향의 반전

v1에서 파싱 버그는 **게이트 우회**였다. v2에서 파싱 버그는 **안내를 한 번 못 띄우는 것**이다. 에이전트 훅이 명령을 놓쳐도 git 훅이 그대로 막는다. **안전이 정확한 파싱에 의존하지 않는다.**

### 3.2 삭제되는 것

`scripts/lib-tokenize.sh` 전체 · `pending-set.sh`의 인자 파싱 · `gate.sh`의 토크나이저·매처·마커 계산·`-C` 해석 · `SKILL.md`의 `<BLOCKED_COMMAND>` 전달과 `'\''` 이스케이프 규칙 · `tests/command-forms.bats`.

## 4. 에이전트 판별 — 3층 구조

D00에 따라 게이트는 **에이전트 커밋에서만** 켜진다. 판별이 틀리면 제품이 틀린다.

### 4.1 왜 환경변수를 1차 신호로 쓰지 않는가

측정으로 확인한 두 가지:

- **`CLAUDECODE`는 문서화된 API가 아니다.** Claude Code 설정 문서에 "서브프로세스로 내보내는 환경변수" 목록 자체가 없다. 이름이 바뀌면 게이트가 **조용히** 꺼진다
- **`AI_AGENT`는 Claude Code의 것이 아니다.** 이 머신에서 관찰된 `AI_AGENT=claude-code_…`는 사용자의 터미널 래퍼(cmux)가 설정한 것이다. 다른 환경엔 없다
- **Codex는 식별용 환경변수를 아예 설정하지 않는다.** 모든 맥락을 stdin JSON으로 넘기고 서브프로세스엔 사용자 셸 환경을 그대로 물려준다

즉 Codex는 환경변수로 판별할 방법이 **없다**.

### 4.2 1차 — 핸드셰이크

**에이전트 훅이 발동했다는 사실 자체가 증거다.** 판별할 필요가 없다.

```
에이전트 PreToolUse 훅 발동
  → $GIT_DIR/quiz-gate/agent-session 에 기록: {agent, session_id, at}
git pre-commit 훅
  → 그 파일이 신선하면(창 안) 에이전트 커밋으로 판정
```

변수 이름을 하나도 보지 않으므로 **에이전트의 어떤 버전 변경에도 살아남는다.** Claude Code와 Codex 모두 `PreToolUse` 훅과 stdin JSON(`session_id`, `cwd`, `hook_event_name`) 스키마가 같아 **같은 스크립트를 쓴다.**

### 4.3 2차 — 환경변수 (알려진 것만)

핸드셰이크가 없을 때의 백업. `CLAUDECODE`, `CLAUDE_CODE_SESSION_ID` 등 **직접 관찰한 것만** 목록에 넣는다. 추측으로 채우지 않는다 — `AI_AGENT`를 넣었다면 남의 환경에서 오작동했을 것이다.

### 4.4 3차 — 음성 신호

`stdin`이 TTY면 사람이 터미널에 있는 것이다 → 막지 않는다.

### 4.5 판정 규칙과 애매한 경우

```
핸드셰이크 신선함        → 게이트
알려진 에이전트 변수 존재 → 게이트
TTY 있음                → 통과
그 외(애매)             → 통과
```

애매한 경우(TTY 없음 + 신호 없음)에는 IDE 커밋, CI, **우리가 모르는 에이전트**가 한 덩어리로 들어온다. 확실히 구분할 방법이 없다.

**D00에 따라 통과가 맞다.** 모르는 에이전트를 잡으려고 IDE 커밋을 막으면, 도구는 문제를 풀지 않으면서 마찰만 만들고 결국 꺼진다. **한계로 명시한다: 지원 목록에 없는 에이전트는 게이트되지 않는다.**

### 4.6 층별 하위호환성

| 층 | 깨지는 조건 | 실패의 성격 |
|---|---|---|
| 핸드셰이크 | 에이전트의 훅 시스템 자체가 바뀜 | **플러그인이 안 뜸 = 시끄러운 실패** |
| 환경변수 | 변수 이름 변경 | 조용한 실패 — 그래서 1차로 쓰지 않음 |
| TTY | — | 사실상 없음 |

## 5. 멀티 에이전트 — 한 저장소, 두 플러그인

Claude Code와 Codex의 플러그인 규약을 실물로 대조한 결과 **경로가 하나도 충돌하지 않는다.**

| | Claude Code | Codex |
|---|---|---|
| 플러그인 매니페스트 | `.claude-plugin/plugin.json` | `.codex-plugin/plugin.json` |
| 마켓플레이스 매니페스트 | `.claude-plugin/marketplace.json` | `.agents/plugins/marketplace.json` |
| 훅 등록 | `hooks/hooks.json` | `hooks.json` (저장소 루트) |
| 스킬 | `skills/<name>/SKILL.md` | **동일** |
| 스킬 프론트매터 | `name` / `description` | **동일** |
| 훅 이벤트·stdin·거부 방법 | — | **동일** |

### 5.1 저장소 배치

```
kkochikkochi/
├── hooks/pre-commit                  게이트. 에이전트 무관          [공유]
├── scripts/
│   ├── stamp-agent.sh                핸드셰이크 기록 + 건강검진      [공유]
│   ├── install.sh                    git 훅 설치·체이닝·제거        [공유]
│   └── record-pass.sh                통과 기록                     [공유]
├── skills/kkochikkochi/
│   ├── SKILL.md                      문항 규칙·채점·오답 루프        [공유]
│   └── ask/{claude-code,codex}.md    질문 제시 방법만 분리          [개별]
│
├── .claude-plugin/{plugin,marketplace}.json                       [Claude]
├── hooks/hooks.json                  Claude 훅 등록                 [Claude]
├── commands/{kk,kk-log}.md           Claude 슬래시 커맨드            [Claude]
│
├── .codex-plugin/plugin.json                                       [Codex]
├── .agents/plugins/marketplace.json                                [Codex]
└── hooks.json                        Codex 훅 등록                  [Codex]
```

**공유를 기본으로 하고 갈라야 할 곳만 가른다.** v1에서 같은 내용을 두 곳에 두면 반드시 한쪽이 낡는다는 것을 반복해서 겪었다.

### 5.2 유일한 실질적 차이 — 질문 제시

**Codex에는 `AskUserQuestion` 대응물이 없다.** 바이너리가 노출하는 로컬 도구는 `shell`과 `web_search`뿐이다.

| | Claude Code | Codex |
|---|---|---|
| 객관식 | `AskUserQuestion` 으로 클릭 선택 | 평문으로 선택지 제시, 사용자가 타이핑 |
| 서술형 | 일반 질문 | 동일 |
| "모르겠다" | 선택지에 포함 | 평문 안내 |

채점·오답 루프·오답 선택지 규칙·정답 위치 무작위화는 **전부 동일하다.** 제시 방법만 `skills/kkochikkochi/ask/<agent>.md` 로 분리한다.

## 6. 설치

### 6.1 왜 별도 단계가 필요한가

측정 확인:

```
훅 설치 후 git status   → 아무것도 없음     (git 이 추적하지 않음)
git ls-files            → 훅 없음           (커밋에 포함 불가)
git clone               → 훅 안 따라감      (클론한 쪽엔 게이트 없음)
git worktree            → 훅 공유함         (추가 처리 불필요)
```

플러그인 설치는 `~/.claude/plugins/` 또는 Codex 캐시에만 파일을 놓는다. 저장소의 `.git/hooks/` 에는 닿을 수 없다. 잊으면 **게이트가 조용히 없다.**

### 6.2 조용한 부재를 시끄러운 안내로

에이전트 훅이 이 문제를 맡는다. 전역이라 설치가 필요 없고, 하는 일은 파일 존재 확인이라 파싱 정확도와 무관하다. 커밋을 볼 때 (a) git 훅 설치 여부, (b) 마커 기록 가능 여부를 확인하고 실패하면 그때 막고 알린다.

### 6.3 에이전트 자율 설치의 경계

안내는 사람이 아니라 **에이전트에게** 한다. deny 사유에 그대로 실행 가능한 명령을 담는다. 경계는 **변경이 git에 추적되는가**로 가른다.

| 상황 | 실효 훅 디렉터리 | 변경 성격 | 처리 |
|---|---|---|---|
| 훅 없음 | `.git/hooks/` | 미추적 · 로컬 · 되돌릴 수 있음 | 에이전트가 바로 설치 |
| 기존 훅 있음 | `.git/hooks/` | 미추적 · 로컬 · 되돌릴 수 있음 | 에이전트가 체이닝 설치 후 보고 |
| `core.hooksPath` 설정됨 | 예: `.husky/` | **저장소에 추적됨** | 사용자 확인 후 진행 |

`core.hooksPath` 가 있으면 `.git/hooks/` 는 완전히 무시되고(측정 확인), 실효 디렉터리는 커밋되는 디렉터리다. 거기 쓰면 `git status` 에 뜨고 커밋에 섞인다. 남의 저장소에 추적되는 변경을 말없이 만드는 것은 자율의 범위 밖이다. `pre-commit` 프레임워크는 이 경우 아예 설치를 거부한다("Cowardly refusing to install hooks with `core.hooksPath` set") — 우리는 거부하되 상황과 선택지를 설명한다.

실효 디렉터리는 `git rev-parse --git-path hooks` 로 얻는다.

### 6.4 체이닝

기존 `pre-commit` 이 우리 것이 아니면:

1. `pre-commit` → `pre-commit.kkochikkochi-chained` 로 이동
2. 우리 훅을 `pre-commit` 으로 설치
3. 우리 훅은 체이닝된 훅을 **먼저** 실행하고, 0이 아니면 그 종료 코드로 즉시 끝낸다

**순서의 근거** — 린트·포맷·테스트가 거부하는 코드에 이해도 퀴즈를 내는 것은 순서가 틀렸다. 어차피 커밋되지 않을 코드다.

**관례에서 벗어난다는 점을 명시한다.** 조사 결과 `pre-commit`·`husky`·`lefthook` 중 **기존 훅을 실행하는 도구는 없다.** 보존만 한다. `pre-commit` 은 한때 실행했다가 걷어냈고, 체인지로그에 그 흔적이 남아 있다(1.4.4 "Guard against infinite recursion when executing legacy hook script", 1.6.0 "legacy … are now invoked", 이후 제거).

그들이 겪은 실패 모드에 대한 우리의 대응:

| 실패 모드 | 대응 |
|---|---|
| 무한 재귀 | 자기 식별 마커로 "내 훅은 다시 체이닝하지 않는다"를 보장. 체이닝은 1단계로 제한 |
| 이중 실행 | 재설치는 멱등. 체이닝 파일을 덮어쓰지 않는다 |
| 남의 훅 계약을 모름 | 먼저 실행하고 0이 아니면 즉시 중단. 인터리빙 없음 |

**자기 식별 마커**는 `pre-commit` 방식을 차용한다 — 생성한 훅 안에 고정 문자열을 심고, 설치 시 파일 내용에 그것이 있는지로 "내 훅인가"를 판별한다.

제거는 이 과정을 정확히 되돌린다.

## 7. `--no-verify`

`--no-verify` 는 git 훅을 건너뛴다(측정 확인). 에이전트 훅이 명령 문자열에서 감지해 deny한다.

여기서는 부정확해도 안전하다. 오탐이면 질문 한 번, 미탐이면 v1과 같은 노출일 뿐 새로 나빠지지 않는다. **단순 문자열 포함 검사로 충분하며 토크나이저를 다시 들이지 않는다.**

## 8. 메시지 원칙

git 훅의 stderr 는 **에이전트 종류를 가정하지 않는다.** git 훅은 사람이 직접 커밋할 때도 실행될 수 있고(핸드셰이크가 신선한 경우), Claude Code 전용 문구를 쓰면 Codex 사용자에게 무의미하다. 범용 문장을 쓰고 에이전트별 안내는 그 위에 얹는다.

## 9. 유효한 v1 결정

그대로 유지: 통과 토큰의 blob SHA 바인딩(D08), HEAD 무효화 안 함(D09), `covered.tsv` + `passes/` 분리(D11), 문항 예산과 축(D02·D17·D19·D20), 근거 없는 문항 폐기(D14), 신뢰 경계(D10), 하드 게이트(D01), 오답 루프와 탈출구(D03·D06).

`record-pass.sh` 는 명령 문자열 인자를 잃고 `git diff --cached` 만 쓴다. 저장 형식과 검증 규칙은 그대로다.

## 10. v2에서 남는 한계

- **`--no-verify`** — 에이전트 훅이 놓치면 우회된다
- **지원 목록에 없는 에이전트** — 게이트되지 않는다. D00에 따른 의도된 선택
- **`core.hooksPath` 저장소** — 사용자가 확인을 거부하면 게이트가 없다
- **훅 미설치 + 에이전트 훅도 놓침** — 게이트가 없다. v1과 같은 노출이며 새로 나빠지지 않는다
- **팀 공유** — git 훅은 클론을 따라가지 않는다. 저장소에 커밋되는 디렉터리 + `core.hooksPath` 가 정석 경로지만 §6.3의 추적 문제와 정면으로 만난다. v1 범위 밖
